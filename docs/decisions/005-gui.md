# 005: GUI

Status: accepted (2026-10-13)

## Context

The GUI ([002](002-technology-stack.md)) is one React app for the Desktop, browsers and later the phone. It shows many kinds of content side by side: the Daemon, Events, later Repositories, Terminals, Agents and files. How content is named, placed and kept is costly to change once there are many Views. How the Server serves the GUI, the token and the Content-Security-Policy are in [004](004-server.md).

## Decision

- **Terms:** a View shows something, by its kind and parameters; a Panel is a tab showing one View; Groups hold Panels as tabs, side by side or stacked; the Layout arranges the Groups ([glossary](../glossary.md)). dockview (`dockview-react`) provides Panels and Groups.
- **Views know nothing of dockview:** `gui/web/src/views/` has a folder per kind, named with its icon in `views/kinds.ts` and its component in `views/index.ts`; a View gets its parameters as props, with ways to change them and its tab's title. Only `layout/` uses dockview (a lint rule), so that a phone shell can show the same Views as pages, and dockview's frequent major versions stay in one place. Views open other Views through `useOpenView` (`views/opening.ts`), which `layout/` provides with our `openView`, never dockview's API: from a Panel's Group from within it, elsewhere from the active Group (`layout/ViewOpener.tsx`), e.g. from the status bar, whose Daemon icon, coloured by the Daemon's health, opens the Daemon View.
- **Addresses:** a View's address is written as a URL's path, query and fragment, each part's values encoded (`URLSearchParams`), the parameters sorted: its kind and its parameters say what it shows, `events?repository=…`; its fragment how it is looked at, e.g. sorted or searched, `diff?…#find=beta`. A parameter with several values repeats, `kind=clone&kind=worktree`. Each View decides which part a value goes in as it sets it: what changes which things it shows (a filter, a comparison) is a parameter, what only changes how they are shown (their order, a search in them) is in the fragment. Addresses differing only in their fragments name the same View (`viewKey`): a link to it marks it as shown and focuses it, as it is looked at there; going back and forward steps through fragments too. A Panel keeps its View's address in dockview's Panel parameters, which the View can change, e.g. by filtering, and are saved with the Layout; its ID is random, as a Panel's View can change. Opening a View that a Panel shows focuses that Panel, its tab flashing in the accent for a moment to show where it is; two Panels may show the same View. How the phone shell maps addresses to page URLs is decided with it; the page's own fragment carries the token (`#token=…`).
- **Opening:** "+" in each Group's tab bar lists the kinds that stand alone (not Changes, Diff or History, which need a Checkout); an empty Group lists a few to start with; a View opens others as previews, e.g. by a `ViewLink`, a button with the kind's icon (and its name, where there's room; a View's bar ends in icons alone), greyed out where it would show nothing that needs a look, e.g. a Checkout without changes. Changes come as a pair, wherever a commit's or a Checkout's uncommitted ones are linked: Changes, then Diff, all files one under the other (`views/changes/ChangesLinks.tsx`). A commit is named as its icon and short hash, as text, then that pair, lined up in lists (`CommitHash`); not in the pickers' lists, which offer choices, nor in the commit's line in a bar, which already links to the other View. A link opens by a click in its own Group, by the middle button or Alt+click beside it, as browsers open a link in place or in a new tab (Ctrl and Shift stay free for selecting in lists). Beside is the Group touching it on the right, else below, left or above; of several on that side, the topmost (right, left) or leftmost (below, above), by their sizes on screen (`layout/beside.ts`); a Group alone is split, to the right. A preview is one per Group, which the next preview replaces, also the one that opened it (the Panel stays, its View changes), its title in italics; it is kept, an ordinary Panel, once its tab is double-clicked (not a link: its second click would land in the View opened), it is changed (filtered, sorted, …), or it is dragged to another Group. Previews are a Panel parameter beside its View's, so the Layout keeps them. Later also from sidebars (dockview's edge groups) and a command palette.
- **Saving:** the Layout is kept per browser, in localStorage, with a format number. A Panel whose kind no longer exists says so; a View that fails, e.g. on parameters it no longer understands, shows its error in its Panel only; a View of a Checkout notes a failed request above what it showed before, which stays, greyed out, and once the Checkout is gone says so in place of all of it, either linking to the Events that tell what happened (`views/CheckoutError.tsx`); a Layout that can't be restored gives the default one. No migrations.
- **Keys:** Ctrl+W closes the active Panel (or empty Group); only the Desktop passes it to the page, as browsers close their tab. Ctrl+F goes to the active Panel's search field, the one its View names (`views/keys.ts`), or presses the button opening it, e.g. the Diff's find bar; else the browser finds in the page. Each Group goes back and forward through the Views it showed, as a browser tab does (`layout/visits.ts`): by the mouse's side buttons over a Group's tabs, View or placeholder, or Alt+←/→ in the active one, which the page takes from the browser. Each address a Group shows is a step: another Panel's, or another in the same Panel (a link replacing a preview, a filter, another Revision compared), but keys typed in a row, e.g. a search, are one, until typing is done: Enter, or leaving the field (a run's number in `layout/dock.ts`). Going back shows a View again in its Panel, or as a preview where the Panel is gone. The steps are kept until the page is left.
- **Empty Groups:** a Group stays when its last Panel closes or moves away (dockview's `closeEmptyGroups: false`), offering Views to start with, so a Layout keeps its shape; an empty Group, but not the last, offers to close, as does Ctrl+W.
- **Views built once shown, then kept drawn:** a Panel's View is built when its tab is first shown, so a restored tab never looked at costs nothing (a Diff asks for no files; its tab keeps the title its Layout saved); from then on it stays drawn while hidden (dockview's `always` renderer, for all Panels), so that it keeps its scroll positions, and showing it again lays nothing out anew, e.g. a Diff's lines. Views are drawn over their Groups, not in them, so where an element sits says nothing of its Panel or Group: shortcuts act on dockview's active Panel or Group, reaching into a View through its Panel's context, and the mouse's side buttons act on the Group our tab, View or placeholder belongs to; a lint rule (`gui/lint/dock-elements.grit`) rejects reading dockview's elements.
- **Later, Workspaces:** one window switches between Workspaces, ordered by hand (lists of Repositories are ordered by name or activity instead), e.g. one per Repository, each with its own Panels in a named Layout that Workspaces share (at first, all the same one). Each Workspace keeps its own dockview, all of them mounted and the hidden ones not asking again until shown; a shared Layout that changed is applied when its Workspace is shown. This needs Groups that stay when empty.
- **Live updates:** the GUI asks the Server again only when its live connection hints at a change, never on a timer (`api/live.ts`, which maps each hint to the queries it covers, by the names in `KEYS`); connecting asks again for everything, and gaining focus (TanStack's `focusManager`, for which the page's window gaining it counts too, e.g. back from the editor) asks for a pass and for what changes by hand: the settings, and Checkouts' changes, as editing a file changes no State. Answers stay current until then (`staleTime: Infinity`). It reconnects after 1, 2, 4 … 30 s, and at once on focus; 25 s without a heartbeat count as lost. The status bar says live or since when disconnected, the Daemon's icon turns lost, and the Daemon View says what to check.
- **Lists:** TanStack Table (`@tanstack/react-table`, headless) holds a list's columns and their state; Views render them as CSS grids of their own markup (`components/table/`). A row opens its details by the button in its first cell, or by a click anywhere else on it but on its cells' own buttons and links, and not one selecting text. Tooltips are native (`title`): a cell's own where it adds something (a full time, a status spelled out), else its whole text, as it may be cut off; a header's says what the column shows, if its label doesn't. Columns may sort (TanStack's sorting, off unless a column turns it on; the order in the address's fragment, `sort`), rows may hold rows (`getSubRows`, `data-depth`), which rows that fold open instead of details (the Changes View's groups, directories with changes, and new folders, whose files are asked for once opened), rows that open another View instead, as a link does (a changed file its Diff), marked while that View is shown in any Group, focused or not, as VS Code marks the file of the editor shown (`useIsShown`, from `layout/`; also a commit in History while its Changes are), and rows that show all they have open nothing (a note), and a filter may be linked: set only from outside, e.g. by a link, and offered only while set. A list shows its rows in columns or each in two lines, a choice in its View's bar (`table`, and our `TableLines`), until chosen as the device starts: two lines where the main pointer is coarse, a phone's or tablet's. In columns, every column is as wide as set, none taking the rest: wider than the list, they scroll sideways, header and all; narrower, the room left stays blank. In two lines, a row shows its square and icons beside what it is, its details below, one after the other rather than in columns, which would only line up by chance, and times at the end, where they line up; the Changes View's rows stay in one line, so it has no choice, and the Database View's tables, of any columns, only columns. A list scrolls itself, filling what its View leaves below its bar (`ViewPage`), so that its header and its sideways scrollbar stay in view; one that is part of a page, the Diff's untracked files, only sideways. Column widths can be dragged, and a double click on a column's edge fits it to its loaded cells, at most as wide as the list. In columns, the header's context menu (the right button; a long press on Android) shows or hides columns, moves the one clicked left or right, past those shown, and resets the list's look, its layout too. Dragging a header with a mouse moves its column too (React Aria's `useDrag`, the header row its `useDrop`): to the gap between the headers shown nearest to where it is dropped, an accent line showing which while dragging; with a finger, whose long press opens the menu, its ← and → instead. Only columns with a header are arranged so; those without (a square, a logo, links) stay in place. A column saying what a row is (a name, a path, a subject, a summary, a message) always shows, as does one filtered or sorted by, hidden or not, and the Database View's last one shown. In two lines, the View places the cells, so hidden columns and their order apply only to columns, and the header is a line of buttons instead: one per filter, named by its column (the square's by what it filters, `priority`, `level`), saying what it is set to and opening its choices; one clearing them all while any is set; at the end, the column sorted by, opening the others, each first sorted as its header would, and its direction, turning it round in one click. What a list keeps, its widths, hidden columns, order and layout, is kept per kind of View in the browser (`hephaistos.lists.<kind>.<part>`; the Database View's per table, the Diff's untracked files sharing the Changes View's), shared by all its Panels, and not part of addresses. Widths reach the grid as CSS variables. A column's header filters by it: one choice for a point on a scale (a priority or higher, since a time), any of several for a set (kinds, Repositories), none meaning all. Filters are the View's parameters, by the names of the API's, which filters like the CLI; so they are saved with the Layout, and the tab's title names them.
- **Controls:** React Aria Components (`react-aria-components`, unstyled), styled with our tokens, for controls beyond the browser's own: menus and popovers (the "+" menu, column filters: a menu for one choice, a dialog for many), opened by our own buttons (`Pressable`) for their tooltips; a search field (`components/SearchField`), its text in the View's parameters at each key, asked with once typing pauses (`useDebounced`) or on Enter; a Revision picker (`components/GitRevisionPicker`): fixed rows (working tree, index, HEAD) and tabs of branches, tags and commits, as each use chooses, after All, a few of each with a row leading to their tab; typing shows All, filtered (refs in the browser, ranked: the same name, starting with it, at a word's start, within; commits searched by the Server, from HEAD or everywhere), an exact name or a hash's commit on top; a kind's tab lists all of it (virtualized, commits loading more on scrolling); Enter picks the first row, and with none resolves the text as git does; Ctrl+←/→ between tabs. Refs are named by their full names (`refs/heads/main`), never mistaken for another ref or a Revision, and shown short.
- **Diffs:** the Diff View shows git's patch of one file (`diff?clone=…&from=…&to=…&path=…`), or without `path` a stack: all files of the comparison or commit one under the other, in the order Changes lists them (Changes links to it at its bar's end). Its words, in code and here:
  - *A diff's lines*: the patch's, with `gui.diff.context` lines around each change; *collapsed* lines, the unchanged ones left out between changes or up to the file's end (but one alone, which shows instead, once the file's versions are known; `UNCOLLAPSED`), once *expanded* by their *separator*, a bar standing in for them; with *Whole file* on, all of them, expanded. Find searches them, wherever the diff is scrolled and whether its file is folded.
  - *Drawn*: lines the renderer has made elements for, those near the view (its `Virtualizer`); only what is shown on them, e.g. find's marks, depends on it.
  - *Fold*: a file or directory in a stack reduced to its header, by a click on it; its lines are still its diff's. Folding lets go of its diff: unfolded, its expanded lines are collapsed again. Lines collapse, files and directories fold.
  - *Large diff*: one with more lines changed than `gui.diff.large_lines`, which waits to be shown by its button, so that drawing it can't slow down the page unasked; Whole file doesn't show it.
- **Rendering:** a diff is filled in with the file's two versions, asked for after its patch, so that it says how many lines it leaves out up to the file's end, and its collapsed lines expand; rendered by `@pierre/diffs`, pinned, imported only by `components/diff/` and loaded once a diff shows, so another renderer could replace it; Shiki highlights it with the themes `gui.code.theme_light` and `gui.code.theme_dark` name, on the page's background, in Web Workers (a diff shows as plain text until its colours come); its header is ours, as the file's row in Changes shows it, and stays in view below the View's bar while its diff does; separators show as quiet gaps between two lines, not the renderer's bars, so that where a file starts stands out. An empty diff offers where the file's changes are now, in the same Panel.
- **Stacks:** each file as high as its lines are likely to be until it comes near the scrolled area, then asked for, shown with its versions (asked for again, e.g. on focus or a live hint, a new patch shows once its versions came too, and unchanged ones leave it as it is), and held as high as its patch's rows and separators make it until drawn, so that it changes height once, if at all (`components/diff/height.ts`); once asked for, kept however far it is scrolled. Files under their directories' headers (nested, in their parents', as Changes nests them), which stay in view above the file's header and line up with it. A click on a file's or directory's header folds it, and another unfolds it (a directory's files as they were); what is folded stays so in all the Checkout's Diffs, in every comparison, until unfolded, kept per browser (`hephaistos.folds.diff`; the Changes View keeps its own folds so, `hephaistos.folds.changes`), each part of a View apart from others showing the same directories: the stack and its untracked files, each group of Changes, a directory's fold holding for all below it however its header reads (one by its path below a folded one says so, and shows with it); a choice in the bar folds all files at once, leaving their headers as an index, or unfolds all (neither marked while mixed). Untracked files and new folders, which may be anything left lying about, come last, listed as Changes lists them, each file's diff shown below its row once opened, or all at once.
- **Look:** side by side (inline in narrow Panels; a new or deleted file's lines on their own side, as other files' are) or inline, wrapped or scrolled, Whole file or not (turned off, the diff starts anew, as the renderer can't collapse lines again): chosen for all Diffs, kept per browser (`hephaistos.diff`).
- **Finding:** a Diff finds in its diffs' lines (a drawn diff's renderer says which lines it has), one file's or a stack's, from a row below its bar (`components/find/`), opened by a button at the bar's end or Ctrl+F: as typed, or matching case, whole words, or a regular expression (JavaScript's, with `\w`, `\b` and `\d` meaning words and digits in any script, as whole words do); which match of how many, from the first, Enter and Shift+Enter to the next and the one before, Escape closing it. A stack's files are asked for all at once as the row opens, with their new versions, page by page (`/api/diffs`), and searched in the stack's order, untracked files only while their rows are open, after the others; stepping to a match in a folded file unfolds it, in a large diff shows it, for good, as a click would (typing leaves them). Matches are marked on the lines drawn, the current one stronger, its line too, by the CSS Custom Highlight API in the renderer's shadow DOM, again as it draws; the current one is brought into view, also from lines not drawn yet. What is looked for is in the address's fragment while the row is open (`find=`, and `case`, `word`, `regex` while on), the current match isn't. Matching runs in a Web Worker, ended after 5 s, so that a regular expression running away can't hang the page; on the page only where there are no workers (WebKit's tests).
- **Comparisons:** the Changes and Diff Views show first in their bar what they compare: two Revisions picked (`from` ⇄ `to`, swapped by a button between), or for a commit (`commit=`) its line in their place, opening all about it below the bar, with a button to pick other Revisions instead, from its first parent; without `from` and `to`, Changes shows HEAD → working tree, in `git status`'s groups or together, a choice at the bar's end offered only for that pair and kept per browser (`hephaistos.changes`), as the Diffs' look is. Directories show each by its path or nested in their parents (one holding a single directory and nothing else joined with it, `src/hephaistos/`), a choice in both Views' bars (in the Diff's only for all files, whose order it sets), kept per browser with the other. Below, what the comparison holds, its files and lines, is the first row of the list or the stack, its lines lined up with the rows' and headers', scrolling with them; a Diff's file header names the file and its lines, not the comparison again.
- **History:** the History View lists a Checkout's commits as `git log` walks back (`history?clone=…`), from HEAD or a branch, tag or commit picked (`ref`, HEAD as none, following what is checked out), of all files or one path (`path`), a file's renames marked where they happened, and only commits whose message has all words searched for (`search`, in any order and case), or, for a hash, its commit first, else where it is: on other branches, offered to show it there, or not changing the path, offered with all files; a row opens all about its commit (the commit box, also under a commit's Changes and in a commit Event's details); while HEAD's commits show, a row above them says what isn't committed, with its Changes and Diff. A commit's Changes and Diff (`changes?clone=…&commit=…`, `diff?…&commit=…`) are against its first parent, and say if no branch or tag leads to the commit any more, and what amends of it led to. History opens from a Checkout's row in Repositories, and from the bars of its Changes and of a file's Diff.
- **Later, other Machines' logs:** logs aren't synced, so another Machine's log comes from that Machine's Server, once the GUI reaches other Servers (decided with remote Machines). The Log View takes the Machine as a parameter, `log?machine=…`, this Machine without one, chosen above the list rather than filtered: a log is one Machine's at a time.
- **Look:** CSS modules and the custom properties of `theme.css`, with VS Code's greys; dockview's light theme for sizes, with its colours from `theme.css` (`layout/dock.css`), so it follows the system's light or dark. Each look is set in one place: `theme.css` names the colours, sizes, widths, opacities, weights and fills; the controls' looks (icon buttons, text actions, link buttons, fields, menu items) are `components/controls.module.css`, text's (notes, cut-off text, code, figures, dimming, a page's padding) `components/text.module.css`, used directly, composed (`composes:`) or through components (`IconButton`, `ViewBar`, `ListTable`, which also draws groups of rows, a two-line layout's quieter second line and figures for times and counts, by column). A class composing a look sets none of its properties again, as the build keeps no order between stylesheets; variants go through the custom properties a look reads, which what holds it may set too (`--icon-size`, `--icon-pad-y`, `--icon-pad-x`, `--inline-margin`, `--inline-start`, `--item-padding`), and a second class on the same element names both (`.link.named`). So a View's bar sizes all it holds alike: its buttons and links as large as a `Choice`'s halves, fields keeping text-sized icons. Inline styles hand the stylesheets only values known at runtime, as custom properties (`components/cssVars.ts`). Enforced: `styles.test.ts` fails on colours, sizes (but 1px hairlines, `ch`, `lh`, percentages and viewport units), opacities, weights and state fills of a stylesheet's own, and on a composed property set again; a lint rule (`gui/lint/inline-styles.grit`) on other inline styles. Fills by state: hover, under the pointer, or in menus and pickers under the keys too, is grey (lighter for rows, `--fill-hover-row`, than for controls and menu items, `--fill-hover`); a control's lasting state, on (a toggle on, a choice's way taken), a stronger grey (`--fill-on`); content marked (a row whose View is shown, the picked Revision) the accent (`--fill-marked`), the only fill in it. What is on or marked is a step stronger again under the pointer or the keys (`--fill-on-hover`, `--fill-marked-hover`). Keyboard focus also outlines a control in the accent; a resize line is grey under the pointer and the accent while dragged. Monochrome icons from Lucide (`lucide-react`), mapped in `icons.tsx` by Event kind, action and entity type, a dot for anything else; a test requires one for every kind and chassis. One per entity: a Repository a book, a Clone a git folder, a Worktree a folder tree, a Filesystem a drive, a Mount a linked folder, a Machine by its chassis (a laptop, a monitor, a server, a box for a vm or container, …; a computer if unknown); the Repositories View two books, as several of them. A commit is git's commit (Lucide's `git-commit-vertical`); the History View two on one line, following each other as it lists them, drawn as Lucide would (`drawnIcons.ts`, as the stacked Diff's several pages); git's branch icons stay for branches, and for a graph of them, if one comes. Registering and unregistering show the entity's icon with + and − where Lucide has one (book, folder), else a square's; git adding and removing, a diamond's, after git's logo; what observing finds, a circle's (missing, found). Entity icons show where a row's type isn't otherwise clear, e.g. an Event's subject, not in the Repositories tree. Icons beside text sit a little above the middle of its capitals, by two values in `theme.css` (`--icon-drop` inline, `--icon-lift` when centred), not by nudges per icon: a `TextIcon` (`components/TextIcon`) lines up either way, sized by its context (`--icon-size`). An icon beside text labels it and does nothing on hover; an icon alone is a button (`IconButton`), muted until hovered or focused, its label its tooltip. Monospace among text is a little smaller (`--mono-size`), as its letters look larger. What Views show takes its size and font from `[gui.text]`, code from `[gui.code]` (`look.ts`); tabs, View bars and the status bar keep theirs, so zooming isn't needed to read. Tabs are at most `--tab-width` wide, a longer title cut off; the whole title is the tab's tooltip. A choice between two ways of showing, e.g. side by side or inline, is a `Choice` in the View's bar: both ways' icons, the one taken on, each with its tooltip, a click taking the other. Lines between Groups and between a list's groups of rows have their own colours (`--divider`, `--line`). Brand logos only for links to forges (`forges.ts`), from Simple Icons (`simple-icons`, CC0, imported one by one). Each kind of View has one, shown before its tab's title (`layout/ViewTab.tsx`, around dockview's own tab) and in the lists of kinds.

## Rejected

- A Layout per Repository: rearranging one wouldn't rearrange the others, as with separate VS Code windows.
- Swapping Panels when switching Workspaces: it would recreate every View, losing Terminals' state and scroll positions.
- Layouts in the Registry: an arrangement fits a screen, not every device.
