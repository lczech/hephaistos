# 005: GUI

Status: accepted (2026-10-13)

## Context

The GUI ([002](002-technology-stack.md)) is one React app for the Desktop, browsers and later the phone. It shows many kinds of content side by side: the Daemon, Events, Repositories, Checkouts' changes and history, later Terminals, Agents and files. How content is named, placed and kept is costly to change once there are many Views. How the Server serves the GUI, the token and the Content-Security-Policy are in [004](004-server.md).

This ADR records the decisions that are costly to change. The design built on them is described in [docs/gui/](../gui/): [layout](../gui/layout.md), [interaction](../gui/interaction.md), [looks](../gui/looks.md), [lists](../gui/lists.md), [views](../gui/views.md) and [data](../gui/data.md).

## Decision

- **Views, Panels, Groups, Layout:** a View shows something, by its kind and parameters; a Panel is a tab showing one View; Groups hold Panels as tabs, side by side or stacked; the Layout arranges the Groups ([glossary](../glossary.md)). dockview (`dockview-react`) provides Panels and Groups.
- **Views know nothing of dockview:** only `gui/web/src/layout/` uses dockview (a lint rule); Views get their parameters as props and open other Views through our own `useOpenView`. So a phone shell can show the same Views as pages, and dockview's frequent major versions stay in one place.
- **Addresses:** a View's address is written as a URL's path, query and fragment: its kind and parameters say what it shows (`events?repository=…`), its fragment how it is looked at (`diff?…#find=beta`). Panels keep their View's address, so it is saved with the Layout, linked, and stepped through by going back and forward. How the phone shell maps addresses to page URLs is decided with it.
- **The Layout is kept per browser:** in localStorage, with a format number and no migrations; an arrangement fits a screen, not every device.
- **Views built once shown, then kept drawn:** a Panel's View is built when its tab is first shown and stays drawn while hidden (dockview's `always` renderer), so restored tabs cost nothing and shown again keep their scroll positions. Views are drawn over their Groups, not in them, so nothing reads dockview's elements (a lint rule).
- **Live hints, not polling:** the GUI asks the Server again only when its live connection hints at a change, on reconnecting and on focus, never on a timer.
- **Libraries:** TanStack Query for the Server's answers; TanStack Table (headless) for lists, rendered as our own CSS grids; React Aria Components (unstyled) for controls beyond the browser's own; `@pierre/diffs`, pinned, for diffs, imported only by `components/diff/`, so another renderer could replace it; Lucide for icons, Simple Icons only for forge logos.
- **Looks:** CSS modules and the custom properties of `theme.css`; each look is set in one place and shared, enforced by tests and a lint rule, so that the GUI looks consistent as it grows.
- **Later, Workspaces:** one window switches between Workspaces, e.g. one per Repository, each with its own Panels in a named Layout that Workspaces share (at first, all the same one). Each keeps its own dockview, all mounted, the hidden ones not asking again until shown. This needs Groups that stay when empty.
- **Later, other Machines' logs:** logs aren't synced, so another Machine's log comes from that Machine's Server, once the GUI reaches other Servers (decided with remote Machines): `log?machine=…`, chosen above the list rather than filtered, as a log is one Machine's at a time.

## Rejected

- A Layout per Repository: rearranging one wouldn't rearrange the others, as with separate VS Code windows.
- Swapping Panels when switching Workspaces: it would recreate every View, losing Terminals' state and scroll positions.
- Layouts in the Registry: an arrangement fits a screen, not every device.
